# 号池调度增强（冷却、分层尝试、权重恢复）设计

- 日期：2026-11-17
- 状态：方案已于 2026-11-17 经用户分段确认，待审阅本文档
- 范围：后端（Go）、新前端（web/src）、经典版（web/classic）
- 不在本文范围：号池接入（供应商专用推送凭证、推送模板、key 去重、推送后立即生效、失效 key 自动清理、禁用通知汇总），另行设计，见第 10 节

## 1. 背景

### 1.1 使用方式

- 第三方供应商调新建渠道接口（`POST /api/channel/`）持续推 key，每个 key 一个渠道（单 key 渠道）。
- 同一分组里有 100–1000 个渠道（含已失效未删除的），还混有用户自有的稳定渠道，要能配置推送渠道和自有渠道的先后。
- 推送的 key 既会彻底失效（额度用完、封号、key 无效），也会临时故障（429 限流、偶发 5xx、连接失败）。
- 生产为单节点部署。

### 1.2 现有选路与问题

- 选渠道（`model/channel_cache.go` 的 `GetRandomSatisfiedChannel`）：同分组同模型的渠道按优先级分档，第 N 次重试用第 N 高的档，档用完停在最低档；档内按权重随机。
- 重试时不排除已试过的渠道，可能再次抽中刚失败的那个。每重试一次就降一档：想多试几个推送的 key，只能把它们拆成多个优先级。
- 失败只有"立即禁用"一种处理（`service/relay_error.go` 的 `ProcessChannelError`）。429、5xx 这类临时错误，要么加进禁用状态码（等恢复测试才能回来），要么不加（坏 key 继续接流量，全靠重试兜底）。
- 权重是固定值，渠道恢复后立即按满权重接流量。

## 2. 目标与非目标

目标：
- 临时故障的渠道自动冷却一段时间，冷却期间不参与选路，连续失败时冷却时长翻倍；连续冷却达到次数上限才转为自动禁用。
- 同一优先级可以先试多个渠道再降档，重试不再选这次请求里已经失败过的渠道。
- 冷却结束或恢复启用的渠道先按部分权重接流量，成功后逐步恢复到配置权重。
- 上游整体故障时不把整档渠道都转成禁用。
- 能在日志详情和渠道列表里看到冷却状态和换渠道的原因。
- 默认关闭，升级后行为与现在一致。

非目标：
- 不改表结构，不加表。
- 不修改数据库里的权重值，权重的升降只在内存里生效。
- 多 key 渠道不做按 key 冷却，维持现在按 key 禁用的逻辑。
- 不做多节点间的冷却状态同步（单节点部署；以后可换成 Redis）。
- 不做按延迟、在途请求数打分的自适应调度。
- 不提供手动解除冷却的按钮（编辑渠道或手动改状态会清除冷却记录，见 3.3）。

## 3. 行为规则

### 3.1 何时走新调度

同时满足以下两条时，选渠道走新调度：
1. 开启了内存缓存（`common.MemoryCacheEnabled`；开了 Redis 会自动开启，否则需设 `MEMORY_CACHE_ENABLED=true`）。
2. 开启了冷却（`cooldown_enabled=true`），或"同一优先级最多尝试"大于 1。

否则完全走现有代码（`model.GetRandomSatisfiedChannel`）。没开内存缓存时，设置页给出提示。

"失效错误码"（4.1）属于自动禁用规则，与是否走新调度无关，只要开启了全局自动禁用就生效。

### 3.2 失败归类

每次失败按以下顺序归为一类：

| 顺序 | 类别 | 判断条件 |
|---|---|---|
| 1 | 不处理 | 多 key 渠道；客户端已断开（请求上下文已取消）；本地错误（错误类型为 new_api_error，且不是渠道错误、也不是 `do_request_failed`）；带"跳过重试"标记的非渠道错误 |
| 2 | 失效 | 命中现有的自动禁用规则：渠道错误（`channel:` 前缀）、自动禁用状态码、失败关键词，以及新增的失效错误码。判断时不看全局自动禁用开关 |
| 3 | 临时故障 | 错误码为 `do_request_failed`（连不上上游），或状态码命中冷却状态码 |
| 4 | 不处理 | 其余情况，例如 400、413 |

状态码用的是经过渠道状态码映射之后的值，和现有的重试、禁用判断一致。

处理方式：
- 失效，且全局自动禁用和渠道自动禁用都开启：走现有禁用流程，不另做冷却。
- 失效，但全局或渠道的自动禁用关闭：按临时故障处理（冷却）。
- 临时故障：冷却（需开启冷却）。
- 未开启冷却时，第 2、3 类只走现有流程，不记录冷却。

为此把 `service.ShouldDisableChannel` 拆成"全局开关检查"和"是否命中禁用规则"（`IsChannelDisableError`）两部分，现有调用方行为不变。

### 3.3 冷却状态

每个渠道最多一条内存记录：

| 字段 | 含义 |
|---|---|
| 连续冷却次数 | 中间没有成功的冷却次数 |
| 冷却开始时间 | 最近一次冷却开始的时刻 |
| 冷却结束时间 | 晚于当前时刻即为"冷却中" |
| 权重系数 | 1/4、1/2 或 1；不在冷却且小于 1 即为"恢复中" |
| 最后一次错误 | 状态码和错误码，供渠道列表展示 |

每次尝试记下开始时间（`RequestPolicyState.AttemptStartedAt`，在 `BeginAttempt` 里设置）。**冷却开始之前就已发出的尝试，结果一律不计**，包括失败和成功。这样一批并发请求同时返回 429 只算一次，冷却前发出、冷却后才成功的请求也不会提前结束冷却。

计入的临时故障（尝试开始时间不早于冷却开始时间，且当前不在冷却中）：
1. 连续冷却次数加 1，记为 k。
2. 如果 k 达到"连续冷却几次后禁用"（值大于 0），且全局自动禁用和渠道自动禁用都开启，且通过 3.4 的整体故障保护：改为请求禁用渠道（禁用原因见 5.4）。然后把记录重置为连续冷却次数 0、权重系数 1/4、冷却开始时间为现在、冷却结束时间清空，渠道被恢复测试重新启用后从 1/4 权重开始。
3. 否则开始冷却：时长 = min(首次冷却秒数 × 2^(k−1), 最长冷却秒数)，冷却开始时间为现在，权重系数置为 1/4。

冷却中或迟到的失败：不计数，只记一条"已在冷却中"的决策记录。

计入的成功（尝试开始时间不早于冷却开始时间）：
- 连续冷却次数清零。
- 如果当前在冷却中（例如经冷却兜底或"严格"会话选中的渠道成功了）：立即结束冷却，权重系数保持不变。
- 否则权重系数翻倍，最大为 1。
- 权重系数为 1、连续冷却次数为 0 且不在冷却中时，删除这条记录。

清除记录：
- 编辑渠道（`UpdateChannel` 成功后）。
- 手动改渠道状态：单个、批量、按标签的启用或禁用。
- 恢复测试自动启用渠道时不清除，渠道从 1/4 权重开始。

记录只存在内存里，重启后清空。冷却关闭后，选路不再参考已有记录，记录自然过期。

### 3.4 整体故障保护

转为禁用之前，先看失败渠道所在的同分组、同模型、同优先级这一档：如果这档至少有 4 个渠道，且算上这个渠道一半以上都在冷却中，判定为上游整体故障，只冷却、不禁用，并记一条决策记录。分组取本次尝试实际选中的分组，模型取原始请求模型。

保护只拦截"连续冷却转禁用"，不影响失效错误（401 等）的现有禁用。

### 3.5 选渠道

替换 `service/channel_select.go` 里 `CacheGetRandomSatisfiedChannel` 和 `selectChannelAcrossGroups` 中三处 `model.GetRandomSatisfiedChannel` 调用。在单个分组内：

1. 从路由缓存取出该分组、该模型的可用渠道，规则与现有一致：先精确匹配模型名，取不到再用归一化后的模型名，并应用请求的渠道过滤条件。取不到时返回 nil，和现在一样。
2. 按优先级从高到低分档。"已试过"指本次请求已经尝试过的渠道（`use_channel` 记录，跨分组计算）。
3. 依次尝试以下四轮，某一轮选中即返回：
   1. **常规**：按档从高到低。非最低档里已试过的渠道数达到"同一优先级最多尝试"时跳过这一档；在这一档里没试过、也不在冷却中的渠道中按权重随机选一个。最低档不受尝试次数限制。
   2. **忽略尝试上限**：按档从高到低，在没试过、也不在冷却中的渠道里选。
   3. **冷却兜底**：在没试过、但在冷却中的渠道里，选冷却最先结束的；同时结束的取优先级高的。
   4. **重复使用**：在全部渠道里选。有不在冷却中的渠道时，取其中优先级最高的一档按权重随机；都在冷却就选冷却最先结束的。
4. 第 1 轮里有更高的档因为达到尝试上限被跳过时，记"这一档已试满，降到下一优先级"（只因没有可选渠道而跳过的档不记）；第 3 轮记"冷却兜底"；第 4 轮记"重复使用已试过的渠道"。这些事件先暂存在请求状态里，由 `BeginAttempt` 在 `channel_selected` 之前写入，带上本次尝试的序号。

因为第 4 轮覆盖全部渠道，有候选渠道时不会因为冷却返回 nil，不会出现"无可用渠道"的报错。

权重：有效权重 = 配置权重 × 权重系数（冷却关闭时系数恒为 1）。保持现有语义：同一轮的候选里只要有一个有效权重大于 0，权重为 0 的渠道就不会被选中；全部为 0 时等概率选。

分组切换（auto 分组、多分组令牌）的状态机不变，仍按重试次数判断何时换到下一个分组。新调度不再用重试次数（`priorityRetry`）决定档位，档位只由上面的四轮规则决定。

尝试次数举例：推送渠道优先级 100，自有渠道 10，同一优先级最多尝试 3，最多重试次数 4。共尝试 5 次：前 3 次在推送渠道里选（每次换一个没试过的），后 2 次在自有渠道里选。

### 3.6 会话保持

在 `SelectChannelForRequest` 里，绑定的渠道在冷却中（新调度开启时）：
- "优先"模式：这次跳过绑定的渠道，走正常选渠道，但不解除绑定，也不在请求成功后把绑定改到新渠道（`RecordChannelAffinity` 检查跳过标记后直接返回）。记一条"会话绑定的渠道在冷却，这次换别的渠道"，写入方式同 3.5 的选渠道事件。
- "严格"模式：照旧使用绑定的渠道。

### 3.7 不受影响的路径

- 固定渠道：令牌指定的渠道、任务回原渠道（`LockedChannel`）、按类型选渠道（`GetRandomSatisfiedChannelByType`）。
- 多 key 渠道：不冷却，不调整权重；作为候选参与选路时权重系数恒为 1。
- 渠道测试：测试流程只对失效错误调用 `ProcessChannelError`，所以测试失败不会触发冷却。

## 4. 配置

### 4.1 配置项

新增配置组 `channel_scheduling_setting`（`setting/operation_setting/channel_scheduling_setting.go`，注册到 `config.GlobalConfig`），全部属于请求策略配置：

| 键 | 类型 | 默认 | 取值范围 | 界面位置 |
|---|---|---|---|---|
| `channel_scheduling_setting.cooldown_enabled` | bool | `false` | | 渠道健康 → 临时故障冷却 |
| `channel_scheduling_setting.cooldown_status_codes` | string | `429,500-503,505-523,525-599` | 状态码规则，写法同自动禁用状态码；可为空（只有连不上上游时冷却） | 同上 |
| `channel_scheduling_setting.cooldown_base_seconds` | int | `30` | 1–3600 | 同上 |
| `channel_scheduling_setting.cooldown_max_seconds` | int | `600` | 1–3600；小于首次冷却时按首次冷却计 | 同上 |
| `channel_scheduling_setting.disable_after_cooldowns` | int | `5` | 0–100，0 表示只冷却不禁用 | 同上 |
| `channel_scheduling_setting.disable_error_codes` | string | 空 | 一行一个；去掉首尾空白，忽略空行；不区分大小写的精确匹配 | 渠道健康 → 自动禁用规则 |
| `channel_scheduling_setting.tier_attempt_limit` | int | `1` | 1–100 | 会话与重试 → 重试预算 |

常量（不做成配置）：整体故障保护的最小档位渠道数 4、比例 1/2；权重恢复 1/4 → 1/2 → 1。

### 4.2 保存与校验

- `model.IsRequestPolicyOption` 接受 `channel_scheduling_setting.` 前缀；`requestPolicyDefaultOptions` 加入该组默认值。
- `model.BuildRequestPolicy` 校验上表的范围，拒绝该前缀下的未知字段；解析结果放进 `RequestPolicySnapshot.Scheduling`（冷却状态码区间、时长、失效错误码集合等）。请求路径只读这份快照，不读配置结构体。
- 后端不做跨字段校验：最长冷却小于首次冷却时，运行时按首次冷却封顶。两套前端在提交前拦下"最长冷却小于首次冷却"。这样经典版逐键并发保存时，不会因为中间状态被拒。
- 新增的范围校验错误用 `common.NewMessage` 的英文句子，并加入新前端 7 个语言文件；`UpdateRequestPolicy` 改用 `common.ApiErrorStatus` 返回，响应里带上消息键和参数，前端据此翻译。
- 新前端通过现有的 `PATCH /api/option/request_policy` 一次提交所有改动；经典版沿用逐键 `PUT /api/option/`。

## 5. 可见性

### 5.1 决策记录

`service.PolicyEvent` 新增两个可选字段：`cooldown_count`（第几次冷却）和 `cooldown_seconds`（冷却秒数），都带 `omitempty`。新增的事件：

| 时机 | Action | Reason | Source | 附带字段 |
|---|---|---|---|---|
| 选渠道（加在 `channel_selected` 之前） | `route` | `priority_limit_reached` | `routing` | |
| 同上 | `route` | `cooldown_fallback` | `routing` | |
| 同上 | `route` | `tried_channel_reused` | `routing` | |
| 会话保持跳过 | `route` | `session_channel_cooling` | `session_rule` | |
| 失败后（在 `ProcessChannelError` 写错误日志之前记录，错误日志里能看到） | `health` | `cooldown_started` | `cooldown` | 次数、秒数 |
| 同上 | `health` | `already_cooling` | `cooldown` | |
| 同上 | `health` | `cooldown_disable_requested` | `cooldown` | 次数 |
| 同上 | `health` | `cooldown_upstream_wide` | `cooldown` | 次数、秒数 |

新前端 `policy-label.ts` 为以上 reason 和 source `cooldown` 增加文案；`decision-record.tsx` 在有附带字段时显示"第 N 次冷却 · M 秒"。经典版没有决策记录界面，不改。

### 5.2 冷却状态接口

`GET /api/channel/cooldowns`，权限 `channel:read`（通过 `channelPermissionRoutes` 注册，同时声明访问令牌规则）。

```json
{
  "success": true,
  "data": {
    "enabled": true,
    "memory_cache_enabled": true,
    "items": [
      {
        "channel_id": 12,
        "state": "cooling",
        "cooldown_until": 1795400000,
        "cooldown_count": 2,
        "weight_factor": 0.25,
        "last_status_code": 429,
        "last_error_code": "rate_limit_exceeded"
      }
    ]
  }
}
```

- `state` 为 `cooling`（冷却中）或 `recovering`（恢复中）；恢复中时 `cooldown_until` 为 0。
- 返回时顺带删除已不存在的渠道的记录。

`GET /api/option/request_policy` 的 `data` 增加 `memory_cache_enabled`，供设置页提示。

### 5.3 渠道列表

只对启用状态的渠道显示：
- 冷却中：标签"冷却中"，悬停显示剩余时间、连续冷却次数、最后一次错误的状态码。
- 恢复中：标签"恢复中 1/4"或"恢复中 1/2"。

数据在列表加载和刷新时请求 `GET /api/channel/cooldowns`，不做实时推送。新前端改 `features/channels/components/channels-columns.tsx` 的状态列，复用 `StatusBadge` 和 `Tooltip`；经典版改 `components/table/channels/ChannelsColumnDefs.jsx` 和 `hooks/channels/useChannelsData.jsx`。

### 5.4 服务器日志和通知

- 开始冷却、转为禁用、整体故障保护拦截各打一行 `common.LogText` 英文日志，并在 `common/log_text.zh-CN.json` 加中文。
- 转为禁用复用 `service.DisableChannel`（在 gopool 里执行，与现有禁用一致），禁用原因为固定句子 `Disabled after repeated temporary failures`（`model.ChannelStatusReasonRepeatedCooldowns`）。新前端 7 个语言文件和经典版 8 个语言文件都加这个键；经典版状态列的原因改为经过 `t()` 显示。
- 冷却本身不发通知；转为禁用沿用现有的禁用通知。

## 8. 风险与取舍

- **改动上游文件**：6.2 的改动集中在少数函数入口，每处几行，主要逻辑放在新增文件里，以减少以后合并上游时的冲突。
- **冷却状态在内存**：重启后全部渠道按健康处理，最坏情况是重启后第一轮请求重新撞上限流的 key，随即重新冷却。
- **转禁用需要恢复测试**：转为禁用的渠道要靠"成功后重新启用"和定时测试才能回来；未开启时只能手动启用。
- **选路开销**：每次选渠道遍历该分组该模型的候选（最多上千个），在单节点规模下可以忽略。
- **整体故障保护的粒度**：按分组、模型、优先级一档判断；同一上游的 key 分散在多个档里时，保护可能偏晚触发。

## 9. 上线配置建议（按本场景）

- 推送参数：`weight` 至少为 10（不要为 0）；`supply_type: "pool"`；统一标签，例如 `pool-供应商名`；`test_model` 填最便宜的模型。
- 分层：推送渠道优先级 100，自有渠道 10；同一优先级最多尝试 3；最多重试次数 4。
- 冷却：开启；冷却状态码、时长保持默认；连续冷却 5 次后禁用。
- 渠道健康：失败时禁用开；自动禁用状态码 `401,402,403`；失败关键词保留默认，并按上游补充（例如 `billing hard limit`、`api key not valid`、`api key expired`，不要加 `quota` 这类短词）；失效错误码按上游补充（例如 `insufficient_quota`、`billing_hard_limit_reached`、`account_deactivated`）。
- 恢复：定时测试开，模式"仅检查被自动禁用的渠道"，间隔 15–30 分钟，并发 8；成功后重新启用开；健康检查耗时阈值清空或调到 30 秒以上。
- 会话保持：号池用的会话规则不要选"严格"。

## 10. 后续：号池接入（另行设计）

- 给供应商专用凭证，只能往指定号池推 key；分组、地址、优先级由管理员预先配置。现在供应商需要 `channel:sensitive_write`，能建任意地址的渠道、删除任意渠道，新建渠道的审计也不记地址和分组。
- 推送时对 key 去重；推送后立即刷新路由缓存（现在 `AddChannel` 不刷新，最长等 `SYNC_FREQUENCY`）。
- 新推上来的渠道从 1/4 权重起步（复用本文的权重恢复）。
- 失效 key 定期清理，不误删手动禁用的渠道；禁用通知汇总成一条；供应商可查询自己哪些 key 已失效。
